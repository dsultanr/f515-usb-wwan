# Почему обычной маршрутизации приложениям не хватает

Вендор держит правило `ip rule` `9999: from all lookup main` — раньше любых fwmark-правил,
так что **root/adb-сессии** после `ip route replace default dev <wan> table main` сразу
получают интернет через модем. `<wan>` — это `ppp0` для Huawei/PPP или USB-сетевой
интерфейс (`eth1` и т.п.) для HiLink; дальше в примерах `ppp0`, для HiLink всё то же
самое со своим именем интерфейса.

**Приложения** маршрутизируются иначе: `ConnectivityService` помечает их сокеты fwmark'ом
конкретной сети и заворачивает в её собственную таблицу (`ip rule` приоритет 13000/14000,
`fwmark ... lookup <interface>`) — правило `9999`/`main` для них не участвует вообще.

На этой прошивке штатный TBOX физически снят, но Android продолжает держать для него
"призрачную" сотовую сеть (`vlan72`) — единственную с `CELLULAR`/`INTERNET`-возможностями,
когда Wi-Fi выключен. Таблица `vlan72` указывает `default` на несуществующий шлюз
(`192.168.72.1` — постоянная (permanent) ARP-запись без реального устройства позади).
Трафик приложений, попавший в эту таблицу, просто проваливается в пустоту.

## Фикс

```sh
ip route replace default dev ppp0 table vlan72 metric 5
```

Название интерфейса `wwan-up.sh` не хардкодит, а берёт из `dumpsys connectivity`
(секция `type: Tbox`).

**Насколько эта строка нужна — зависит от прошивки, и на стенде она оказалась лишней**
(замер 2026-08-16). Правило `9999: from all lookup main` стоит выше fwmark-правил сети
(13000/14000), поэтому трафик приложений разрешается в `main` и до таблицы `vlan72`
не доходит:

```
# ip route get 8.8.8.8 mark 0x50066
8.8.8.8 dev ppp0 src 10.67.56.134 mark 0x50066
```

То есть интернет приложениям даёт `default dev ppp0 metric 20` в `main`, а не правка
таблицы `vlan72`. Строка оставлена как страховка для голов с другим порядком правил —
стоит она одного `ip route`. (В более ранней редакции этого документа значилось обратное:
что промаркированный `ping -m` не проходит без этой правки. Прямой замер этого не
подтверждает.)

DNS самой этой сети (`192.168.72.1`) отдельно: адрес внутри подсети `vlan72/24`, для него
маршрут per-host (`scope link`) важнее любого `default` в той же таблице — сколько ни клади
в default, DNS-запрос всё равно уйдёт в тот же мёртвый L2. Поэтому адрес DNS-сервера
дополнительно подменяется DNAT'ом на настоящий резолвер (модема или оператора) — после
DNAT пакет уже вне подсети и идёт по (уже исправленному) `default`.

```sh
iptables -t nat -A OUTPUT -d 192.168.72.1 -p udp --dport 53 -j DNAT --to-destination <настоящий-dns>:53
iptables -t nat -A OUTPUT -d 192.168.72.1 -p tcp --dport 53 -j DNAT --to-destination <настоящий-dns>:53
iptables -t nat -A POSTROUTING -s <адрес-vlan72> -o ppp0 -j MASQUERADE
```

Обе части входят в стадию `--system` `wwan-up.sh` и идемпотентны — повторный запуск не
дублирует правила.

В отличие от правки таблицы, **DNAT — часть рабочая и несущая**: счётчик правила на стенде
показывал 3548 пакетов, то есть через него идёт весь резолвинг головы. Убери его — и имена
перестанут разрешаться совсем (`ping -m <fwmark> 192.168.72.1` — 100% потерь).
`MASQUERADE` относится не к маршрутам, а к этому же пути: запрос уходит с адресом `vlan72`
(`192.168.72.4`), и без подмены источника ответ не вернулся бы.

## Кастомный DNS

Цель этого же DNAT можно задать вручную — это и есть «кастомный DNS для приложений»:

```sh
wwan-up.sh --dns=1.1.1.1   # запомнить и применить сейчас
wwan-up.sh --dns=auto      # вернуться к DNS оператора/модема
wwan-up.sh --dns           # показать, что стоит сейчас
```

Адрес хранится в `state/dns` (кнопка «DNS» в приложении пишет туда же) и применяется при
каждом подъёме, включая автозапуск после ребута. `WWAN_DNS` в `wwan.conf` или в окружении
главнее файла. При смене адреса скрипт снимает своё прежнее правило — иначе первым в
цепочке сработало бы старое и настройка молча ничего бы не изменила; чужие правила на
53-м порту он не трогает, только показывает в логе.

Другого места для этой настройки на голове нет, и это не выбор из удобства:

* приложения резолвят через `netd`, а тот берёт адреса резолвера из конфигурации своей
  сети (фантомной TBOX), а не из `/etc/resolv.conf`;
* легаси-команды `ndc resolver setnetdns` на прошивке нет — `500 0 Command not recognized`;
* «Приватный DNS» в настройках Android — это DoT по имени хоста, IP-адресом его не задать
  (и он перебивает наш DNAT: если включён, запросы уйдут на 853/tcp мимо правила).

Автоматический режим по-прежнему уступает живому DNS сети: если штатный `192.168.72.1`
вдруг отвечает, правило не ставится. Явно заданный адрес ставится всегда — настройка,
которая молча не применилась, хуже отсутствующей.

## VPN-клиенты (HAPP, v2rayNG, WireGuard)

То самое правило `9999`, на котором держится вся раздача интернета приложениям,
ломает `VpnService`.

Android заворачивает трафик приложений в туннель правилами netd на приоритетах
**13000** (secure VPN) и **21000** (bypassable VPN — обычный, не always-on случай).
Оба числа больше 9999, то есть вендорское правило проверяется раньше. Пока в `main`
нет `default`, это никому не мешает: lookup ничего не находит, ядро идёт дальше по
списку и доходит до правил VPN. Но `--system` кладёт в `main` именно catch-all — и
с этого момента `9999` матчит всё подряд, от любого UID, независимо от fwmark. В
`tun0` не приходит ни одного пакета.

Клиент при этом показывает «подключено», и честно: его собственный сокет до сервера
— обычное соединение, оно тоже уходит через модем, хендшейк проходит. Заворачивать
в туннель просто нечего.

Побочно ломается и «Блокировать соединения без VPN»: правило запрета у netd тоже
ниже 9999 и не срабатывает. То есть это не «VPN не работает», а утечка мимо туннеля.

### Фикс

Правило не удаляется, а разбирается на две части — оно нужно вендору ради
конкретных маршрутов в `main` (подсети модема, LAN HiLink'а, служебные интерфейсы),
и разрешать их рано как раз правильно. Мимо туннеля не должен уходить только
`default`:

```
9998:  from all lookup main suppress_prefixlength 0   # всё, кроме default
...    правила netd: VPN 13000/21000, default network 23000
23500: from all lookup main                           # default, но последним
```

`suppress_prefixlength 0` убирает из выдачи ровно маршруты с длиной префикса `<= 0`,
то есть один `default`. Место `23500` выбрано ниже правила default-сети (23000), но
выше `unreachable` (32000): если сотовая сеть не провалидировалась и netd не выбрал
default-сеть вообще, `main` остаётся последним резервом и голова не теряет связь.

Включается ключом или настройкой, по умолчанию выключено:

```sh
wwan-up.sh --vpn        # перенести сейчас, связь не трогая
wwan-up.sh --vpn=off    # вернуть как было
echo 'WWAN_VPN=1' >> /data/local/tmp/wwan.conf   # применять при каждом подъёме
```

Правила `ip rule` не переживают перезагрузку, так что худший исход любой ошибки —
ребут. Тем не менее порядок операций внутри выбран так, чтобы голова ни на одну
команду не оставалась без `main`: сначала ставится catch-all на новом месте, потом
половинчатое правило на старом, и только потом снимается оригинал. Если ядро не
умеет `FRA_SUPPRESS_PREFIXLEN`, скрипт откатывается сам и говорит об этом. После
переноса делается `ip route get` — если непомеченный трафик (adb, watchdog, сам
скрипт) перестал разрешаться, откат происходит без вопросов.

### Мёртвый маршрут в таблице `vlan72`

В режиме VPN защищённый сокет самого клиента (`VpnService.protect()`) уходит уже не
через `main`, а через таблицу выбранной сети — ту самую `vlan72`. И тут вылезает
то, чего раньше никто не замечал, потому что всё разбирало правило `9999`:

`add_default "$TB_IF" 5` кладёт маршрут с метрикой 5, а штатный `default via
192.168.72.1` netd ставит **без** метрики, то есть с нулевой. Ноль лучше пятёрки —
мёртвый маршрут выигрывает отбор, а наш лежит рядом и не используется. Прежняя
проверка этого не ловила: она смотрела, есть ли наш маршрут, а не выигрывает ли он.

Поэтому в режиме VPN чужие `default` из этой таблицы сначала снимаются. Только в
нём: без VPN таблица всё равно не участвует, а трогать маршруты netd без нужды
не стоит — он переставит их при первой переконфигурации сети, и watchdog будет
чинить это по кругу.

### DNS: подмена источника не только для модема

Одного переноса правил мало. Рядом с DNAT стоит:

```sh
iptables -t nat -A POSTROUTING -s <адрес-vlan72> -o <wan> -j MASQUERADE
```

Запрос netd уходит с адресом `192.168.72.4`, и без подмены источника ответ не вернётся.
Но привязка к `-o <wan>` исходит из того, что DNS всегда уходит через модем — а это верно
ровно до тех пор, пока трафик не начинает попадать в туннель. После DNAT адрес назначения
уже внешний, и при работающем `VpnService` он резолвится в `tun0`, а не в `<wan>`.
MASQUERADE не срабатывает, запрос уходит в туннель с адресом `192.168.72.4`, на той
стороне не значащим ничего, и ответ вернуться не может.

Симптом коварный: клиент честно показывает «подключено», маршруты в порядке, счётчики
`tun0` растут, `nslookup <имя> 1.1.1.1` из root-шелла отвечает — а приложения получают
`ERR_NAME_NOT_RESOLVED`. Разница в том, что у `nslookup` адрес назначения внешний с самого
начала: DNAT не участвует, источник выбирается как `10.0.0.1`, ответ приходит.

Поэтому такое же правило ставится и для туннеля:

```sh
iptables -t nat -A POSTROUTING -s <адрес-vlan72> -o tun+ -j MASQUERADE
```

Без VPN оно не срабатывает никогда — `tun0` просто нет, — так что ставится безусловно.

## Результат

После этой правки `dumpsys connectivity` показывает сеть `Tbox` как
`everValidated{true}`/`lastValidated{true}`, `Active default network` переключается на неё
(даже с выключенным Wi-Fi), и обычные приложения — не только root-шелл — получают
интернет через модем.
